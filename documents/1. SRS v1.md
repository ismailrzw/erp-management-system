## 1. EXECUTIVE SUMMARY

The PBL Management System is a web-based platform for Beaconhouse National University to manage the entire lifecycle of Problem-Based Learning (PBL) / Final Year Project (FYP) workflows. The system automates student group formation, project evaluation, iterative submissions, and departmental/institutional oversight — replacing ad-hoc email and spreadsheet-based processes with a centralized, role-based digital system.

**Core value:** Students form groups online (transparent, trackable), evaluators score work on standardized rubrics, HODs visualize departmental progress, and the Dean sees university-wide formation metrics — all in real time, all auditable.

**Out of scope:** Individual project details beyond the group name/title, course management beyond FYP courses, financial tracking, or integration with Banner/institutional ERP systems (future scope).

### 2.2 User Roles (6 total, role-based access control, server-side enforced)

| Role | Description | System Access | Key Workflows |
|---|---|---|---|
| **PBL Manager** | Administrator, one per course/institution | Full CRUD on all entities, approves groups, assigns evaluators, publishes iterations/surveys/announcements | Seed students, manage group lifecycle, assign projects to evaluators |
| **Student** | FYP participant, scoped to own account | Create group (becomes leader), browse/request to join groups (same course+section only), submit work, fill surveys, view own evaluations | Form groups, submit iterations, see grades |
| **Evaluator** | Scorer, can be internal faculty or external industry | Scoped to assigned groups only | See assigned groups, score rubrics per iteration, submit exhibition evaluation, log supervision meetings |
| **HOD** | Department Head, tied to one department, read-only | See all groups in own department only, view charts, export PDF | Monitor departmental progress, identify bottlenecks |
| **HOD I&C** | Head of Innovation/Coordination, same permissions as HOD but separate account | See all groups in own department only | Backup oversight, cross-department coordination |
| **Dean** | University administration, read-only, cross-department | See all groups, all departments, students-without-group list | Strategic oversight, institutional metrics |

**Access control rule:** All queries are server-side filtered — a student's login token contains their `role` and `dept`; the API never trusts `?dept=SE` in a request, it uses the token's dept claim or denies the request. This is non-negotiable.

## 3. FUNCTIONAL REQUIREMENTS BY MODULE

### 3.1 Authentication & Authorization (Module #1)

**FR-1.1:** System shall support login via email + password (no social login, no self-signup).
- Students log in with their roll-based email (`ROLL@SUPERIOR.EDU.PK`) + manager-generated password.
- Teachers/Evaluators log in with their institutional email + manager-set password.
- Manager has a fixed admin account.

**FR-1.2:** Upon successful login, system shall issue a JWT token with claims: `{sub, role, dept, refId, iat, exp}`.
- Token expiry: 8 hours for interactive sessions.
- Refresh token: optional, not required for v1.

**FR-1.3:** System shall enforce role-based route protection server-side via decorator `@role_required("manager", "student", ...)`.
- Any endpoint without this decorator is accessible only to authenticated users (no public access except `/api/auth/login`).
- Attempting to access a route with insufficient role shall return `403 Forbidden`.

**FR-1.4:** System shall support "logout" by client deleting the token from localStorage; no server-side session table required.

**FR-1.5:** System shall enforce `dept` scoping for HOD/HODIC queries — a HOD's token contains `dept: "SE"`, and any request for group lists is implicitly filtered to that dept on the server.

### 3.2 Reference Data Management (Module #2)

**FR-2.1:** System shall support CRUD operations for:
- **Departments:** `{code, name, deleted}` — soft-delete pattern, recoverable.
- **Courses:** `{name, dept, minGroup, maxGroup, deadline, deleted}` — group size limits are per-course, deadline is course-level.
- **Teachers:** `{name, email, dept, type (Internal Faculty / External Industry), deleted}` — doubles as the Evaluator pool.
- **Students:** `{name, roll, dept, section, session, course, teacher, email, password_hash, recoveryEmail, deleted}` — soft-deleted (recovered from recycle bin).

**FR-2.2:** System shall support bulk import of students via CSV/Excel:
- File contains: Name, Roll, Dept, Section, Session, Course, Teacher, Recovery Email (optional).
- System auto-generates email as `ROLL@SUPERIOR.EDU.PK`, auto-generates password (bcrypt hashed).
- System sends credential email to each imported student.
- System logs import results: imported count, duplicate count, error rows.
- A student with the same roll or email cannot be imported twice (unique constraint).

**FR-2.3:** System shall support individual student add:
- Optionally accepts a personal recovery email field.
- Sends credential email on creation.

**FR-2.4:** System shall support soft-delete + recover for all reference entities:
- Deleted entities are marked `deleted: true` but retained in the database.
- They do not appear in normal queries (filtered out server-side).
- An admin can recover deleted entities via a "Recycle Bin" UI.

**FR-2.5:** System shall filter student lists by department, section, and session:
- Manager can view students with combined filters: `GET /api/manager/students?dept=SE&section=A&session=Fall%202025`.
- Pagination optional but recommended (default 50 per page).

### 3.3 Group Formation (Module #3 — Critical Path)

**FR-3.1:** A student may create a group:
- Request: `POST /api/student/groups` with `{name, projectTitle}`.
- Creator automatically becomes the **leader**.
- Status: initially `pending` (awaiting manager approval).
- Constraints: student cannot create a group if they are already a member of any group (enforced server-side via Mongo query).

**FR-3.2:** A student may browse joinable groups:
- Request: `GET /api/student/groups/browse`.
- Returned groups meet all: same course, same section, not full (members.length < max), not created by the requester (not their own group).
- A student cannot browse groups outside their course/section (enforced server-side, not just UI filter).

**FR-3.3:** A student may send a join request to a group:
- Request: `POST /api/student/groups/:id/join-request`.
- A student can only send a join request if not already in any group (checked server-side).
- Implicitly, if the student has a pending join request to another group, the new request **cancels the old one** automatically (a student can only have one active pending request at a time).
- A student cannot send a join request if the group is at max capacity (checked server-side at request time).

**FR-3.4:** A group leader receives join requests and must approve or reject:
- Request: `POST /api/student/join-requests/:id/accept` or `reject`.
- **Critical rule:** Before accepting, the system re-checks (a) the student is not already in another group (race condition guard), and (b) the group is not over capacity (another leader might have accepted someone in the interim).
- If the check fails, return `409 Conflict` — the requester should refresh and retry.
- If the check passes, add the student to `members[]` and increment the group's `version` field (optimistic locking).

**FR-3.5:** A student may leave a group:
- Request: `DELETE /api/student/groups/:id/leave`.
- If the leaver is the leader **and** others remain: leadership transfers to the next member (order: first in members array).
- If the leaver is the leader and no others remain: delete the group entirely.
- If the leaver is not the leader: just remove them from members[].

**FR-3.6:** A manager may approve a group:
- Request: `POST /api/manager/groups/:id/approve`.
- Status: `pending` → `approved`.
- Only an approved group may be assigned evaluators or start submitting work (enforced at later workflow stages).

**FR-3.7:** A manager may drop (delete) a group:
- Request: `DELETE /api/manager/groups/:id`.
- Hard-delete (not soft-delete) — removes the group and all its join requests. Only a manager can do this (typically for typos or fraud).
- Soft-delete alternative: TBD if needed; for now, hard-delete.

**FR-3.8:** System enforces the **one-student = one-group constraint**:
- At the database level: check `db.groups.find_one({members: studentId})` before adding a student anywhere.
- At the application level: wrapped in a transaction or optimistic-locking (version field).
- A student who is already in a group cannot be added to another group under any circumstance.

### 3.4 Iterations & Submissions (Module #4)

**FR-4.1:** Manager can create course iterations:
- Request: `POST /api/manager/iterations` with `{course, title, details, deadline}`.
- Example iterations: Proposal, Lit Review, Project Code, Final Report, Exhibition.
- Iteration is scoped to a course — all groups in that course see the same iteration.

**FR-4.2:** Manager can attach rubrics to an iteration:
- Request: `POST /api/manager/iterations/:id/rubrics` with array of `{question, weight, levels: {0: "...", 1: "...", ..., 5: "..."}}`.
- Weight is a 0–100% value per question; total weights across all questions sum to 100%.
- A rubric has 6 levels (0–5 point scale) with descriptive text for each level.
- Rubrics are locked after an evaluator submits a score for that iteration.

**FR-4.3:** A student/group can submit work for an iteration:
- Request: `POST /api/student/iterations/:id/submit` with `{note, file}`.
- File is uploaded to Cloudinary (dev) or local storage (prod), returning a public URL.
- Submission is per-group, not per-student.
- After the deadline, submissions are flagged `late: true` but still accepted (no hard cutoff).

**FR-4.4:** System tracks submission state: `{groupId, iterationId, status (submitted/awaiting), file, submittedAt, late}`.

### 3.5 Evaluation & Scoring (Module #5)

**FR-5.1:** Manager can assign groups to evaluators:
- Request: `POST /api/manager/assignments` with `{evaluatorEmail, groupIds: [...]}`.
- A group is assigned to **one evaluator at a time** (not multiple evaluators per group in v1).
- An evaluator can be assigned multiple groups.

**FR-5.2:** Evaluator can score a group's submission per iteration:
- Request: `POST /api/evaluator/evaluations` with `{groupId, iterationId, scores: {q1: 4, q2: 3, ...}, comment}`.
- System calculates weighted total automatically: sum(score[q] * weight[q] for q in rubric).
- Once submitted, the evaluation is **locked** — no edits, no deletes (immutability after submission).

**FR-5.3:** Evaluator can submit a separate exhibition evaluation (final scoring pass):
- Request: `POST /api/evaluator/exhibition` with `{groupId, exhibitionScores, comment}`.
- Exhibition uses a similar rubric (separate collection, not the same as iteration rubrics).
- Also locked after submission.

**FR-5.4:** Evaluator can log supervision meetings:
- Request: `POST /api/evaluator/meetings` with `{groupId, iterationId, title, date, agenda, start, end, minutes, nextMeeting}`.
- Meetings are read-only (no edit), just log entries.

### 3.6 Surveys & Feedback (Module #6)

**FR-6.1:** Manager can create and publish surveys:
- Request: `POST /api/manager/surveys` with `{course, title, questions: [{text, type: "likert"}]}`.
- Likert scale: 1–5 (Strongly Disagree to Strongly Agree).

**FR-6.2:** Students respond to surveys:
- Request: `POST /api/student/surveys/:id/respond` with `{responses: {q1: 4, q2: 5, ...}}`.
- One response per student per survey (idempotent — retaking overwrites the prior response).

**FR-6.3:** Manager views aggregated survey results:
- Request: `GET /api/manager/surveys/:id/report`.
- Response: `{totalResponses, byQuestion: {q1: {mean, median, distribution}}}`.

### 3.7 Announcements & Attachments (Module #7)

**FR-7.1:** Manager can post announcements:
- Request: `POST /api/manager/announcements` with `{title, content, date}`.
- Rich text (HTML) optional.
- Scope: visible to all students/evaluators (no role filtering).

**FR-7.2:** Manager can upload attachments (file library):
- Request: `POST /api/manager/attachments` with multipart file.
- File stored on Cloudinary/local, metadata in Mongo.
- Students can download.

### 3.8 HOD Dashboard (Module #8)

**FR-8.1:** HOD views all groups in their department:
- Request: `GET /api/hod/groups` (server-side filters to HOD's dept from token claim).
- Returns table: Group name, project title, section, members count, status.

**FR-8.2:** HOD views charts:
- Groups by status (approved, pending, rejected).
- Groups by section (if applicable).
- Charts are rendered client-side (React component, no server-side chart generation).

**FR-8.3:** HOD can export as PDF:
- Request: `GET /api/hod/groups/pdf` (server returns a PDF file).
- Alternative: client-side HTML-to-PDF (print stylesheet + browser print) — easier, lower backend complexity.

### 3.9 Dean Dashboard (Module #9)

**FR-9.1:** Dean views department-wise breakdown:
- Request: `GET /api/dean/dashboard` returns table:
  | Department | Total Students | Total Groups | Approved | Pending | Students Without Group |
- All data aggregated across the university.

**FR-9.2:** Dean views students without a group:
- Request: `GET /api/dean/students-without-group`.
- Returns: Name, Roll, Dept, Section, Session.
- Sortable by dept/session.

**FR-9.3:** Dean can export as PDF (same approach as HOD — print stylesheet preferred).

### 3.10 Reporting & Audit (Module #10)

**FR-10.1:** System logs all mutations (group creation, member add, evaluation submit, approval, etc.) with timestamp + actor email.
- Captured in a separate `auditLog` collection: `{timestamp, actor, entity (groups/evaluations/...), action, oldValue, newValue}`.
- Dean + Manager can view this log (read-only).

**FR-10.2:** Soft-deleted entities can be recovered:
- Query: `GET /api/manager/recycle-bin` lists all deleted students/teachers/depts/courses.
- PATCH: `/:id/restore` marks `deleted: false`.

**FR-10.3:** Iteration + evaluation reporting:
- Manager views stats: groups submitted per iteration, average score per iteration, late submissions.

## 4. NON-FUNCTIONAL REQUIREMENTS

### 4.1 Performance
- API response time: <500ms for 99% of requests (excluding file uploads).
- Database query optimization: indexes on `roll`, `email`, `(course, section)`, `(studentId, status)`.
- Frontend: Time to interactive <3 seconds on a 4G mobile connection (Lighthouse target: 80+).

### 4.2 Scalability
- Concurrent users: minimum 500 simultaneous (all students in a single semester).
- Database: MongoDB Atlas free tier (M0) for pilot; scale to M2/M5 for production.
- Horizontally scalable backend (stateless Flask + Gunicorn workers).

### 4.3 Reliability & Uptime
- Target: 99.5% uptime during semester (SLA: 3.6 hours downtime per month acceptable).
- Automated backups: MongoDB Atlas automatic daily backups (retention: 7 days).
- Disaster recovery: database snapshot replication to a secondary cluster if afforded (production).

### 4.4 Security
- **Authentication:** JWT + bcrypt password hashing (not plaintext, not salted MD5).
- **Authorization:** role-based, server-side enforced on every endpoint.
- **Data in transit:** HTTPS only (enforced via Nginx reverse proxy in production).
- **Data at rest:** MongoDB Atlas encryption at rest (default enabled).
- **Secrets management:** environment variables (`.env`) never committed; Render/Vercel manage prod secrets.
- **SQL injection / NoSQL injection:** parameterized queries via `pymongo` (no raw string concatenation); same for Mongo field names.
- **CSRF:** stateless JWT (no session cookies), frontend adds Authorization header manually — CSRF not applicable.
- **Input validation:** all requests validated server-side (schema + business rule checks), client-side validation is UX only.

### 4.5 Usability
- Responsive design: works on desktop (1920px), tablet (768px), mobile (375px+).
- Accessibility: WCAG 2.1 AA target (alt text for images, keyboard navigation, color contrast).
- Language: English (no internationalization in v1).

### 4.6 Auditability
- All state changes logged with timestamp + actor.
- Soft deletes allow recovery and historical inspection.
- Immutable evaluation/exhibition scores (once submitted, no edits).

### 4.7 Maintainability
- Code follows PEP 8 (Python) and ESLint (JavaScript) standards.
- Naming: descriptive, consistent (camelCase for JS, snake_case for Python).
- Documentation: inline comments for non-obvious logic; API contracts in OpenAPI/Postman.
- Testing: unit tests for business logic (e.g., `test_one_student_one_group_constraint`), integration tests for API workflows.

**Data flow (example: group creation):**
1. Student clicks "Create Group" on Vercel frontend.
2. Frontend sends POST /api/student/groups with JWT token (from localStorage).
3. Render/Flask auth middleware verifies JWT, extracts `role` + `refId`.
4. Route handler checks student is not already in a group (Mongo query).
5. Creates group document in MongoDB, sets leader to `refId`, status to `pending`.
6. Returns `{success: true, data: {groupId, name, status}}`.
7. Frontend re-fetches group list, updates `GroupContext`, refreshes UI.

## 8. SECURITY & AUTHENTICATION (DETAILED)

### 8.1 Password Management
- Passwords are **never** stored in plaintext.
- On account creation (bulk import or individual add): generate a password or use the provided one, hash with `bcrypt(password, salt_rounds=10)`, store the hash.
- On login: compare provided password to the hash using `bcrypt.compare()`.
- Password reset: (out of scope for v1, but if added: use a short-lived token sent to email, not security questions).

### 8.2 JWT Token
- **Issued on login:** payload `{sub, role, dept, refId, iat, exp}`, signed with `JWT_SECRET_KEY`.
- **Expiry:** 8 hours (can extend if user interacts regularly, but v1 is simple expiry).
- **Refresh token:** not implemented in v1 — on expiry, user logs in again.
- **Token in request:** sent as `Authorization: Bearer <token>` header (standard).
- **Validation:** verify signature + expiry on every request via `flask_jwt_extended` middleware.

### 8.3 Role-Based Access Control (RBAC)
- **Enforced server-side:** every endpoint has a `@role_required(...)` decorator.
- **No client-side-only checks:** hiding a button in the UI does not prevent a POST if the server doesn't check the role.
- **Role hierarchy:** no inheritance (student ≠ student + manager); a user has exactly one role.
- **Dept scoping:** HOD's token contains `dept: "SE"`; any query to HOD endpoints is filtered by that dept server-side, not trusting the request.

### 8.4 Data Validation
- **Server-side:** all input validated against a schema (request body + query params).
- **Client-side:** HTML5 form validation + JavaScript for UX — never trust it.
- **NoSQL injection prevention:** `pymongo` uses parameterized queries; never construct Mongo queries by string concatenation.
- **XSS prevention:** React escapes JSX by default; announcements (rich text) are sanitized with `DOMPurify` before rendering.

### 8.5 Secrets Management
- `JWT_SECRET_KEY`, `MONGO_URI`, `CLOUDINARY_*` keys are stored in environment variables (`.env`).
- `.env` files are **never** committed to Git (`.gitignore` includes them).
- Production: Render/Vercel secrets UI; university server: systemd unit file with env vars or `/etc/pbl-system.env`.

### 8.6 HTTPS Enforcement
- Development: localhost, no HTTPS needed.
- Pilot (Render + Vercel): automatic HTTPS (managed by the platforms).
- Production (university server): Nginx reverse proxy with Let's Encrypt cert (free, auto-renew).

### 8.7 CORS & CSRF
- **CORS:** Flask-CORS configured to allow requests from Vercel/frontend domains only (not `*` in production).
- **CSRF:** not applicable for stateless JWT (no session cookies). Token is explicitly added by client (Authorization header), not automatically by browser.

## 9. DEPLOYMENT & INFRASTRUCTURE

### 9.1 Development Environment
- **Local machine:** Docker + Docker Compose (backend + frontend + Mongo).
- **Setup:** `git clone` → `cp .env.example backend/.env` → `docker-compose up`.
- **Testing:** Postman (backend), browser dev tools + React DevTools (frontend).

- **Backend:** Render free tier, auto-deploys `develop` branch, pulls `MONGO_URI` + secrets from Render env vars.

- **Database:** MongoDB Atlas M0 (free).
- **File storage:** Cloudinary free account (25 GB, enough for testing).

### 9.3 Production Deployment (University Server)
- **Backend:**
  - Flask app runs under Gunicorn (e.g., 4 workers, port 8000).
  - systemd service file: `pbl-backend.service` manages start/restart/stop.
  - Process manager: **not PM2** (which is Node.js); systemd is the OS standard.
  - Command: `gunicorn wsgi:app --workers 4 --bind 0.0.0.0:8000`.
- **Frontend:**
  - React app built to static files: `npm run build` → `dist/` folder.
  - Served by Nginx (reverse proxy, HTTPS, static file serving).
  - Nginx config proxies `/api/*` to Gunicorn on localhost:8000.
- **Database:**
  - MongoDB Atlas M2 cluster (paid tier for production data volume), or local MongoDB if on-premises is required.
  - Backups: automated daily snapshots.
- **Secrets:**
  - Stored in `/etc/pbl-system/.env` (readable only by the `pbl` user running the service).
  - Sourced by the systemd service via `EnvironmentFile`.
- **HTTPS:**
  - Nginx with Let's Encrypt certificate (auto-renewed via certbot).
  - All HTTP traffic redirected to HTTPS.
- **Monitoring:**
  - systemd logs: `journalctl -u pbl-backend -f`.
  - Nginx logs: `/var/log/nginx/access.log`, `error.log`.
  - Database monitoring: MongoDB Atlas cloud dashboard.

## 10. GIT & BRANCHING STRATEGY

### 10.1 Branch Model
```
main          ← Production-ready, tagged per sprint/release
  ↑
develop       ← Integration branch, CI-gated, team reviews every PR
  ↑
feature/*     ← Individual task branches
fix/*         ← Bug fixes
```

### 10.2 Branch Naming
- **Feature:** `feature/<module>-<short-description>`, e.g., `feature/group-create-endpoint`.
- **Fix:** `fix/<short-description>`, e.g., `fix/race-condition-join-request`.
- **Chore:** `chore/<short-description>`, e.g., `chore/add-mongo-indexes`.

### 10.3 Commit Hygiene
- **Conventional Commits:** `feat(groups): add create-group endpoint`, `fix(auth): correct role claim`.
- **Small, atomic commits:** one logical change per commit, not "fixed everything."
- **No merge commits:** rebase feature branches before merging (keep history linear).

### 10.4 Pull Request Workflow
1. Develop on `feature/...`, push to GitHub.
2. Open PR into `develop` (never directly into `main`).
3. CI runs (lint, tests, build); if red, fix in the same branch, re-push.
4. Requested review from Ismail or Ramsha (code owner + co-lead).
5. Address comments, push fixes to the same branch.
6. Once approved + CI green: squash-merge into `develop`, delete feature branch.

### 10.5 Branch Protection Rules
- **main:**
  - Require PR before merge.
  - Require 1 approval (from Ismail or Ramsha).
  - Require CI to pass.
  - Require branches to be up-to-date before merge.
  - No direct pushes (protected, even for Ismail in practice).
- **develop:**
  - Require PR before merge.
  - Require 1 approval (Ismail or Ramsha).
  - Require CI to pass.
  - Allow force pushes (off) — keep history clean.

## 13. RISKS & ASSUMPTIONS

### 13.1 Technical Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| **Race condition on join-request accept** | Medium | High — could break "1 student = 1 group" | Optimistic locking (version field) or Mongo transactions; test explicitly in CI |
| **Mongo Atlas free tier quota exceeded** | Low (v1) | High — service stops | Scale to M2 cluster; monitor storage + query count; hard cap is 512 MB |
| **Cloudinary free tier limit hit** | Low (v1, limited uploads) | Medium — file uploads fail | Switch to local storage (one-file change); implement quota checks |
| **Deploy-only bugs** | Medium | High | Test against real deployed URL daily, not just localhost; Render/Vercel up on Day 1 |
| **Evaluator loses evaluation work mid-submit** | Low | High — affects grades | Immutability after submit; transaction wrapper around score insert |
| **Bulk import silently fails on bad Excel rows** | Medium | High — 50% of students missing | API always returns error details; never silent partial success |

### 13.2 Assumptions
- **Internet availability:** university has reliable, high-speed internet (5+ Mbps); system is not designed for offline use.
- **Browser support:** modern browsers (Chrome, Safari, Firefox, Edge); IE not supported.
- **Data migration:** no migration from existing systems (legacy papers, emails); starting fresh.
- **User adoption:** assume faculty/students will use the system if it's responsive and intuitive; training provided.
- **Semester timeline:** pilot launch before mid-semester; feedback collected for next iteration.

## 14. GLOSSARY & DEFINITIONS
